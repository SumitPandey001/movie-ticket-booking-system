I have a side question, Who generated the idempotency key which we expect in header. Whose role is to generate and remember that key?

**🤖 Assistant:**

The **client** generates the key: the web or mobile app the customer is using. The server's only job is to remember what it answered for that key.

**Why it has to be the client.** A key is meant to identify one *intent*, such as "I pressed Hold for A1 and A2". Only the client knows whether two requests carry the same intent or two different ones:
- If the server or gateway made the key, every retry would arrive with a fresh one. The server would see two unrelated requests and hold twice, which defeats the purpose.
- The client knows "the network timed out, so I'm sending *the same* request again", as opposed to "the customer changed seats and pressed Hold again".

**What the client does:**
1. When the customer performs the action (taps **Hold seats**, **Pay**, **Cancel**), create a new random UUID.
2. Send it in `Idempotency-Key` on that request.
3. Keep it while that action is unfinished. On a timeout, a dropped connection, a 5xx or a double tap, resend **the same body with the same key**. The server replays the first answer, or does the work if the first attempt never took effect.
4. Once the action is settled (a success, or a 4xx it has shown to the user), throw the key away. The next action gets a new key.

Where it's kept is up to the client:
- **A web app** can hold it in memory, in the checkout screen's state.
- **A mobile app** should persist it, e.g. local storage, for payments. Then it survives the app being killed mid-request, and the customer can't pay twice.

**What our server does:**
- Stores the key per user, with a hash of the request (`idempotency_record`) and the response, for 24 hours (`booking.idempotency-retention`).
- Scopes keys per user, so two customers who happen to pick the same key never collide.
- Rejects mistakes: the same key with a different body gets `409 IDEMPOTENCY_KEY_REUSED`, and the same key while the first request is still running gets `409 IDEMPOTENCY_IN_PROGRESS`.

**The gateway** just passes the header through untouched. It shouldn't generate or rewrite keys, for the same reason as above.

This is the same model Stripe and most payment APIs use: the caller owns the key, and the server honours it.

Keeping request and response DTOs in the same package as their controller is a legitimate pattern, and here it's a reasonable choice. What's actually wrong in this codebase is that it's applied three different ways, and one module doesn't follow it at all.

**Why putting them next to the controller is fine**
- **They belong to the HTTP layer.** A `HoldRequest` or `BookingResponse` exists only to turn JSON into a service call and back, so it lives beside the controller that uses it.
- **Nothing else can import them.** They're package-private (`record HoldRequest(...)` with no `public`). A service or another module can't accidentally depend on the JSON shape.
- **A `dto/` subfolder would weaken that.** Java has no "visible to the parent package" setting, so `web/dto/HoldRequest` would have to be `public` for `web/BookingController` to use it. Spring Modulith would still stop other modules reaching into `internal`, so a `dto/` folder isn't wrong, just less strict.

A `dto/` folder mainly helps when a `web` package gets crowded, say 30 or more files. The biggest here is `catalog/internal/web` with 15.

**What's wrong: three styles in one codebase**

| Style | Where |
|---|---|
| Separate files in `web/` | catalog (`CityRequest`, `CityResponse` …), booking (`BookingResponse`, `HoldRequest` …), show (`CreateShowRequest`, `ShowResponse`) |
| Records nested inside the controller | `CouponAdminController`, `PricingRuleAdminController`, `RefundPolicyAdminController`, plus a few in `BookingController` and `ShowAdminController` |

It keeps the **"seats left" number on the browse page** up to date in Redis without counting seat rows on every page view.

**The idea:** `seats-left:{showId}` in Redis holds how many seats a show has free. Whenever inventory changes seats, `availabilityChanged` announces "this show just gained or lost N free seats", and `SeatCounter` adds that N to the Redis number.

**Where the numbers come from** (`delta` is negative when seats are taken, positive when they're freed):

| Method in `InventoryFacade` | `delta` |
|---|---|
| `hold` | minus the seats that were really `AVAILABLE`. A seat taken over from a lapsed hold was already counted as gone, so it isn't subtracted twice |
| `confirm` | minus only the seats that had become free again (their hold ran out and nobody took them). The customer's own held seats were already subtracted at hold time |
| `releaseHeld`, `releaseBooked` | plus the seats freed |
| `block` / `unblock` | minus / plus the seats that actually changed |

- The Lua script adjusts the counter **only if the key already exists**. A plain `INCRBY` on a missing key would start from 0 and store, say, −2.

- If Redis is down entirely, `seatsLeft` falls back to counting in the database.


It wraps each such method in a small adapter object that remembers two things:

- **when to run it**: for `@TransactionalEventListener` the default is `AFTER_COMMIT`.

**2. Publishing hands the object to the dispatcher**

```java

```

`events` is the `ApplicationEventPublisher`, which is the Spring context itself. Confirmed in Spring 7.0.9's source: after-commit listeners run from `afterCompletion`, and Spring wraps each one in a `try/catch` that only **logs** a failure.

**Short answer:** if two listener methods take the same parameter type, **both are called**, once each, for every event. Spring never picks one. What differs is the order they run in and what happens when one fails, and that depends on the kind of listener.

**1. Plain `@EventListener`: immediate, same thread**

```java
@EventListener void a(SeatAvailabilityChanged e) { … }
@EventListener void b(SeatAvailabilityChanged e) { … }
```

- Both run **immediately inside `publishEvent(...)`**, one after the other, on the publisher's thread and inside its transaction.
- **Order:** add `@Order(1)` / `@Order(2)` to the methods. Without it the order isn't guaranteed.
- **If `a` throws:** `b` is **not called**, and the exception comes out of `publishEvent`, straight into the code that published. Inside `hold()` that would roll back the whole hold. One broken listener can break the publisher.

**2. `@TransactionalEventListener`: after commit, still the same thread** (this is what `SeatCounter.adjust` is)

- Both wait for the transaction to commit, then run one after the other.
- **Order:** again `@Order`, which Modulith respects too (`AnnotationAwareOrderComparator` in the source above).
- **If `a` throws:** Spring catches it and logs "TransactionSynchronization.afterCompletion threw exception". `b` still runs. The booking is already committed and the caller never sees the error. The catch: the failure is only a log line, and nothing retries it.

**3. `@ApplicationModuleListener`: async, own transaction, recorded** (the notification, refund and show-cancel listeners)

- Each listener gets its **own row in `event_publication`**, identified by its `listener_id`. Each runs on its **own background thread**, in its **own transaction**.
- **Order:** none. They run in parallel, so don't write listeners that depend on each other's order.
- **If `a` fails:** only `a`'s row stays incomplete, and the retry job re-delivers the event **to `a` alone**. `b` completed and isn't run again. Failures are fully isolated.

**Where this could matter here:** right now every event in the code has exactly one listener. The one catch applies if you ever **add a second listener to an existing event**, for example analytics on `BookingConfirmed` alongside the emails. That listener would be delivered separately and retried separately, so each listener must be safe to run twice. Ours are, which is why re-delivery is harmless:
- emails and SMS: the `notification_log` claim skips anything already sent;
- refunds: the refund status check;
- bookings: the state checks (confirm, fail and show-cancel skip a booking that has already moved on).

A rule of thumb for choosing:
- **needs to happen, can happen later** (emails, refunds): `@ApplicationModuleListener`;
- **best effort, right after commit** (the Redis counter, cache eviction): `@TransactionalEventListener`;
- **must succeed or fail together with the change**: don't use an event; call it directly inside the transaction.

1. A service calls `publishEvent(...)` inside its transaction, for example `BookingEvents.confirmed` from the confirm step.
2. Modulith inserts one `event_publication` row per matching listener, in that same transaction. If the booking rolls back, the rows disappear with it.
3. After commit, each listener runs on a background thread.
4. When a listener succeeds, its row gets a `completion_date`. When it throws, the row stays incomplete, and the retry job or the next restart delivers it again.

That's also why every listener has to be safe to run twice:
- the notification log skips a message that was already sent;
- the refund status check skips a refund that has already moved on;
- the booking state checks skip a booking that is already settled.

**Why our events land in `event_publication`**
- `spring-modulith-starter-jdbc` auto-configures a JDBC repository (`JdbcEventPublicationRepositoryV2`). Every SQL statement it runs is built from `getTable()`.
- The name is unquoted `EVENT_PUBLICATION`, and Postgres folds unquoted names to lowercase. That's why it matches our `CREATE TABLE event_publication` in V16.
- Nothing in our code or `application.yml` sets the name; we just created the table Modulith expects.

**What you can change** (the only related properties under `spring.modulith.events.jdbc`)

| Property | Effect |
|---|---|
| `schema` | Puts the table in another schema: `schema: outbox` makes it `outbox.event_publication`. The table name itself stays the same. |
| `schema-initialization.enabled` | Whether Modulith creates the table itself. We set `false` because Flyway owns it. |
| `use-legacy-structure` | Uses the older, pre-2.0 column layout. |

Separately, `spring.modulith.events.completion-mode: ARCHIVE` moves completed rows into a second table, `event_publication_archive`. That's the only other table name Modulith uses, and it's derived from the first.

**If you rename the table in a migration** (say `outbox_events`), Modulith still queries `event_publication`, and it breaks in the worst way:
- **Startup:** with `republish-outstanding-events-on-restart: true`, Modulith queries the table as the app starts, so startup fails with `relation "event_publication" does not exist`.
- **Every event publish:** Modulith inserts the row *inside the business transaction*, so the failure rolls the business action back too. Confirming a booking, cancelling, cancelling a show and requesting a refund would all fail, not just the emails.
- **Nothing catches it early:** `ddl-auto: validate` only checks JPA entities, and `event_publication` isn't one. Our tests would fail, though, since so many flows publish events.

**If you really need a different name**, the options, from simplest:
1. **A different schema, same table name:** set `spring.modulith.events.jdbc.schema` and create the table there. This is the supported way.
2. **A view** named `event_publication` over your own table. It works because a simple single-table view in Postgres accepts inserts and updates. But it's a trick the next person has to discover.
3. **Your own `EventPublicationRepository` bean.** Modulith backs off its JDBC one, and you write all the SQL. That's a lot of code to own for a name.

I'd keep `event_publication`. It's Modulith's convention, and anyone who knows Spring Modulith will look for it there. If the goal is keeping infrastructure tables apart from business tables, option 1 does that cleanly: `spring.modulith.events.jdbc.schema: outbox`, plus moving the table in a new migration.
